# サードパーティ依存とサプライチェーン設計

> **翻訳についての注記:** 本ドキュメントは英語原文 `20-production-readiness/03-third-party-dependencies-and-supply-chain.md` を日本語に翻訳したものです。コードブロックおよびMermaidダイアグラムは原文のまま維持しています。

## TL;DR

依存グラフこそ、実際に動いているアーキテクチャだ。ウェアハウスの図には12のサービスが描かれている。しかし `cargo tree`、`pip freeze`、ロックファイルの差分は4000のコンポーネントを示す。その1つひとつに失敗セマンティクス、アップグレード義務、遅延への寄与、データフロー上の義務、そして誰かが火曜日にエンジニアリングの外で変更できる法的条件が付いてくる。**文書化済み**: この領域を定義したインシデントはすべて、遠隔地で起きた可用性か完全性の障害だ。2016年、たった1人で保守されていた left-pad が npm から消えたことでインターネット全体のビルドが止まった。event-stream(2018)と ua-parser-js(2021)は、広くインストールされたパッケージの中で、アカウント乗っ取りが標的型のペイロード生成に至ることを示した。Log4Shell(2021)は、推移的依存経由で到達できるログライブラリが、直接インストールしたこともないソフトウェアで組織をインシデント対応に引きずり込めることを証明した。SolarWinds(2020)は攻撃をベンダーのビルドパイプラインへ移し、xz-utils のバックドア未遂(2024)は sshd がリンクする圧縮ライブラリを狙った複数年にわたるソーシャルエンジニアリングを実見した。

これらの失敗クラスに奇抜なものはない。だからこそ依存の選択はプルリクエストの差分ではなく設計レビューに属する。**推論**: サードパーティ製コンポーネントをファーストパーティより構造的に難しくするのは3つの性質だ。失敗モードを、そのランブックなしに継承する。アップグレード周期がこちらのリリース計画と無相関である。そして可用性目標は、公表されていても「利用可能」の定義がこちらの尾の遅延も依存先の依存先も含んでいない形で測られている。

本章はその表面全体を扱う。実重みを付けた選択基準、計測可能なアーキテクチャ性質としてのロックイン、抽象化の税を払わずに出口をを保つ境界設計、レジストリから署名済み成果物までのサプライチェーン完全性、自社で運用しないコンポーネントのランタイム封じ込め、そして全体がロードマップ付きのセキュリティ負債になるのを防ぐ常設のアップグレード計画。**参照設計**: 本番の依存先には必ず、名前のある担当者、固定されたダイジェスト、宣言済みの失敗バジェット、強制されるタイムアウトとリトライ方針、そして「どう離れるか」を書いた1文を付ける。

## 依存が実際にインポートしているもの

エンジニアは機能を見てパッケージを導入する。組織は同時に6つを継承する。

| 継承するもの | 具体的な形 | 表面化する時期 |
|---|---|---|
| 失敗モード | リトライストーム、無制限キュー、ブロッキングDNS、隠れたコネクションプール、クロック感受性 | 依存先の最初の劣化。たいていピーク時に |
| アップグレード義務 | 推移グラフの増大、放置されたAPI、非推奨、ランタイムEOL | 数か月後、最悪のスプリントで |
| セキュリティ表面 | postinstallフック、デシリアライズ経路、シークレット処理、ネットワーク_egress | ベンダー側であって自社ではない。ビルド時のコード実行は任意コード実行と同値 |
| 遅延と容量のバジェット | 相手のp99にこちらのリトライ、さらに相手のリトライ方針を乗算 | 負荷テストか、本番で |
| データフロー | 何をどこにいつまで保存し、サブプロセッサが見るか否か | 顧客のセキュリティ調査表で。常に手遅れ |
| 法的・商業的条件 | ライセンス義務、価格指標の変更、利用可能範囲の制限 | 契約更新か、30日前告のToSメール |

**推論**: 経験豊富なエンジニアが依存先に対して徹底的に地味なのは非対称性のせいだ。導入の上振れはスプリント1回の節約。下振れは、自分がpushできないリポジトリに根本原因があり、何の義理もない人が所有者であるインシデントだ。この非対称性は、導入の基準が「50行自分で書く」より高く、「競合システムを作る」より低いべきだと語る。

推移グラフはこの効果を複利で増やす。直接依存は決定だが、推移的依存は同じ爆発半径を持つ偶然にすぎない。直接依存だけを数える台帳は、典型的なアプリケーションスタックでは露出を1桁過小評価する。だからこそ本章の有用な指標は解決済みグラフ全体を数える。

## 依存の選び方

候補は汎用的な評価表ではなく、最も露出している失敗に対して採点する。下表の重みはリクエスト経路上のコンポーネントを想定する。ビルド時ツールは保守の厳密さを単純さと交換し、アナリティクスSDKは性能をデータフローの抑制と交換すべきだ。

| 基準 | 見るもの | 良い兆候 | 失格条件 |
|---|---|---|---|
| 保守の健康状態 | PRのマージまでの時間、リリース頻度、オープン課題の古さ、コミット権を持つメンテナ数 | 定期的なリリースおよび公開されたセキュリティポリシー | バス係数1。2年前の「help wanted」課題 |
| 失敗の挙動 | タイムアウトの既定値、リトライ方針、接続プールの境界、サーキットブレーカの有無 | 失敗が設定ではなく既定で安全側 | 「無限リトライ」が既定、タイムアウト不明 |
| セキュリティの実践 | 公開されたCVE対応手順、セキュリティポリシー、リリースの署名可否 | 秘密の報告経路とインシデント開示の実績 | シークレットを平文で扱う設計。issue で修正要求がやり取りされる |
| 性能の実測 | 自分のトラフィック形状でのベンチマーク、アロケーション挙動、GC圧 | 公表値ではなく自分の環境での計測 | 合成ベンチの数字だけで語られる |
| セマンティクスの適合 | トランザクション境界、順序保証、冪等性、時間とタイムゾーンの扱い | 自分のドメイン不変条件を素直に表現できる | 「たぶん最終整合」で曖昧に済まされる |

議論に耐えるヒューリスティクスが2つある。第1に、リクエスト経路では**退屈で古いもの**を優先する。6年安定しているライブラリはすでにサプライズの代価を払い終えている。動きの速いライブラリは学習曲線をこちらのオンコールへ移すだけだ。第2に、**マニフェストの1行ではなく解決済みグラフを数える**。40を引き込むパッケージ1つの導入は、1つの導入とは別の決定だ。保守性が現れるのも消えるのもその差分である。

インフラ級のコンポーネント(キュー、ストリームストア、ワークフローエンジン、ベクトルインデックス、モデルサーバ)では、アプリケーションライブラリで省略できる3つの問いを足す。フェイルオーテスト中にコントロールプレーンを誰が運用するのか。ベンチマーク規模ではなく自分の規模での運用モデルは何か。ローリング再起動でできないアップグレードはどういう形になるのか。

## 計測可能な性質としてのロックイン

ロックインは乗り換えへの感情的な抵抗ではない。出口コストであり、出口コストは別々に積算できる5つの部品に分解できる。

| ロックインの種類 | 機構 | 最も安い緩和策 |
|---|---|---|
| データ形式 | 独自ストレージ形式、論理状態のエクスポート不可、または忠実性を失うエクスポート | 自分が所有する正準表現を保ち、ベンダーのストアをプロジェクションとして扱う(導出プロジェクションの章) |
| APIの形 | ベンダーのリクエスト/レスポンスタイプがビジネスロジック中に散在 | シームでポートする。自分のインターフェース、相手のアダプタ |
| 運用 | 特定プロバイダでしか使えないツール・ダッシュボード・ランブック | プロバイダをパラメータとして名指す宣言的定義から生成する |
| 経済 | エグレス料金、リクエスト単価、保持を推奨するストレージクラス | 導入前にトラフィック10倍のコストをモデル化し、エグレスを設計レビューのチェックリストへ入れる |
| スキルと人員配置 | チーム全員が一つの独自システムに認定されている | スキが希少で長持ちするなら意図的に受け入れる。SQLのラッパーなら抵抗する |

**文書化済み**: 過去10年のインフラ系ライセンス紛争で繰り返されたパターン(オープンコア検索・可観測性・データベースのプロジェクトが宽松ライセンスから source-available やサーバ側条件へ移行し、フォークが続いた)は、ライセンスリスクが法的カレンダーを持つアーキテクチャリスクだと教えている。技術的優位性だけで下した依存決定も、こちらの遅延バジェットに無関係な当事者によって覆されうる。

そこから生むべき規律は安い。重要な依存先ごとに**出口ノート**を1つ置き、代替候補、移動すべきデータ、変更が必要なインターフェースを3文で書く。出口ノートは優れた設計レビューの成果物でもある。「シームを名指しできない」はどんな抽象化論より速いシグナルだ。

安直な処方箋についての警告を残しておく。それ自体のためにプロバイダ非依存の抽象化を作ると、誰のセマンティクスも上手くモデル化しない最小公倍数のインターフェースが生まれ、実際に使う機能すべてで漏れる。抽象化が税に見合うのは、次の3つのうち少なくとも2つが成立するときだ。今まさに第2の実装がある。近い将来に規制上または商業上の理由で必要になる見込みがある。そのシームが自分のドメイン言語を他人の語彙から守る場所になっている。そうでなければベンダーに直接依存し、労力は抽象化ではなく出口ノートに使うべきだ。

## レジストリからランタイムまでのサプライチェーン完全性

最も重要な攻撃表面はライブラリのコード経路ではない。バージョン文字列を実行中のバイト列に変える機械の側だ。以下の各ステップは文書化済みのインシデント・クラスを1つずつ閉じ、しかも合成される。ある場所で必須で別の場所で不要、というものはない。

```text
source            developer machine / upstream release
  |  commit signing, protected tags, release from CI not laptop
  v
build             hermetic builder, no ambient credentials, egress allow-list
  |  reproducible inputs, pinned toolchain, dependency hashes enforced
  v
artifact          image or package produced once, never rebuilt per environment
  |  content digest, provenance attestation, SBOM generated at build time
  v
sign              key held by the build system, short-lived identity, no repo secret
  v
registry          private proxy; upstream mirrors snapshotted and immutable
  |  signature + attestation verification at pull time, not report time
  v
deploy            admission control rejects unsigned or unpinned images
  |  digest pinning in the manifest, mutable tags rejected
  v
runtime           no registry credentials, minimal egress, seccomp/AppArmor profile
```

| 統制 | 何を止めるか | 正しくやるための注意 |
|---|---|---|
| ハッシュ付きロックファイルをコミット | 成果物のすり替え、上流による静かな再パブリッシュ | 解決は1回だけ。デプロイ時に直すのではなくCIでロックファイルのドリフトを禁止する |
| タグではなくダイジェストで固定 | タグの書き換え(コンテナでは合法的で日常的) | ダイジェスト固定および、タグが動いたときに更新変更を開く定期ジョブ |
| 許可リスト付きのprivateレジストリプロキシ | typosquatting、dependency confusion、内部と公開スコープをまたぐ名前衝突インストール | 名前空間分離はプロキシだけでなくクライアント側でも強制する |
| 署名と来歴の検証 | ビルド侵害、無署名の上流成果物 | 取得時またはアドミッション時に検証。誰も読まないレポートは監査人向けの検知統制でしかない |
| SBOM取得(SPDXかCycloneDX) | 「うちは影響を受けるか」を1時間で答えられない | マニフェストではなく解決済みグラフを反映するようビルド時に生成する 

| 密閉かつegress制限付きビルド | インストール時スクリプトがビルド環境の認証情報を読む | ビルド時のコード実行はパイプラインで最も特権の高い瞬間。そのように扱う |
| 最小権限のパイプラインID | 侵害されたプルリクエストからのレジストリ公開 | 公開権限をテスト権限から分離。フォーク由来のPRが本番シークレットに到達できない |
| 可能な範囲で再現可能なビルド | 実行中のバイナリを作ったソースを証明できない | コンパイラや静的ツールチェーンでは現実的。大半のアプリケーションイメージでは目標段階 |

**推論**: 順序が重要だ。レジストリ制御のない署名検証は劇場だ。名前でインストールさせられる攻撃者は、自分が署名したものをインストールさせるからだ。egress制限付きビルドおよびダイジェスト固定および許可リストプロキシは、あらゆるスキャナより実際に多くを捕まえる。意図を検出する代わりに能力そのものを削除するからだ。スキャナは優先付けのために走らせ続ける価値がある。その価値は防御可能なパッチキューであって防止ではない。

そのパッチキューについて。重大度のみのトリアージはノイズを生む。大半の勧告は自分のデプロイでは到達不能だからだ。到達可能性の解析(脆弱な関数が実際に攻撃者制御の入力で呼ばれているか)は「既知の脆弱性1,400件」を、誰かが終わらせられるリストへ変える。そして払い戻せない負債を、サービスレベル目標付きの保守作業に変える。

## 自社で運用しないコンポーネントのランタイム封じ込め

サードパーティサービスは、ブランディングの良い信頼できない依存先だ。失敗バジェットの計算は容赦がない。ベンダーが月間4つの9を約束し、自分の目標が3つの9なら、自社のコードが何も寄与する前にベンダーだけで誤差バジェットの大半を消費する。**推論**: リクエスト経路上の同期サードパーティは、SLO分解で独立したバジェット行を得るか、stale-readセマンティクスを持つ非同期プロジェクションになるしかない。

封じ込めは具体的な機構の集合で、どれも安く、どれも省略される。

- **とにかくタイムアウトを最初に。** 自分の締切より短い回次タイムアウトを設定し、キャンセルを伝播させる。既定が「なし」では、ベンダーの遅延スパイクがスレッドプール枯渇に変わる。相手の遅さが原因の自社障害だ。
- **境界付きリトライおよびジッタおよびリトライバジェット。** ベンダー側も内部でリトライしている可能性と調整する。無調整の方針が2つ重なると、部分的な劣化を全面的な劣化へ変える文書化済みのレシピになる。
- **ベンダー別のバルクヘッド。** 依存先ごとに接続プール・ワーカープール・セマフォ上限を分離し、遅いベンダーは共有プールではなく自分の容量だけを消費する。サーキットブレーカ(依存状態の章)はそのとき境界付きリソースに対して働く。
- **古い値が許容される場所では積極的にキャッシュ。** 権限ルックアップと商品メタデータには否定キャッシュ、明示的な stale-if-error 経路を置き、キャッシュ失効が一斉なサンダリングヘルドへ同期しないようにする。
- **変更系呼び出しには必ず冪等性キー。** ベンダーのタイムアウトは書き込み失敗ではない。操作IDがなければ重複を受け入れるか照合作業を作るはめになる。後者を選ぶことになる。
- **Webフックは攻撃者由来の入力として扱う。** 署名検証、リプレイ防御付きのタイムスタンプ許容範囲、冪等なハンドラ、スキーマ検証に失敗したイベントは誰も読まないデッドレターではなく検疫へ。
- **健全性はベンダーのステータスページではなく挙動で定義する。** ベンダー別の成功率・遅延ヒストグラム・レート制限拒否を第一級の信号として追跡する。ステータスページは連絡路であって指標ではない。

クリティカルパス上のコンポーネントについて、「第2のプロバイダがある」は本番トラフィックで試されるまで仮説にすぎない。実際のフェイルオーバ設計には、設定で切り替えられるルーティング、事前にプロビジョニングされたベンダー別の認証情報とクォータ、両ベンダーに対するコントラクトテストで確認された機能同等性、そしてプライマリを実際に遮断するゲームデーが必要だ(レジリエンステストの章)。コストかセマンティクスのせいでフェイルオーバーが不可能なら、文書でそう述べ、補償統制を記録する。劣化モード、境界付きバックログでのキューおよびリトライ、あるいは明示的な顧客可視エラー状態だ。

## 常設プログラムとしてのアップグレード

アップグレード負債は他の負債と同じく複利で増え、取り巻きの利率は他社が先に進んだ数に比例する。プログラムは派手ではなく、指標は正直だ。

| 実践 | 機構 | 防ぐ失敗モード |
|---|---|---|
| グループ化した自動更新PR | ボットが更新を開く。グループ化でレビューコストを抑制し、パッチとメジャーでレーンを分ける | 1年の凍結が定型的なバージョン上げを書き換えに変える |
| セキュリティ専用の高速レーン | パッチは数時間でレビュー。テストは必須だが設計レビューは不要 | 委員会の開催中に続く数日間の既知の露出 |
| ランタイムとツールチェーンのEOLカレンダー | ベースイメージ、言語ランタイム、マネージドエンジンのバージョンを日付で管理 | 四半期で最も忙しい週の強制移行 |
| 依存先の所有者台帳 | すべての直接依存に所有チームと担当エンジニア | 午前3時に「これ誰が承認した?」へ沈黙で答える |
| 削除を第一級のタスクにする | 依存先削除は追加と同じ見積もりを当てる | 誰も触れないゾンビ統合 |
| ベンダーに対するコントラクトテスト | レスポンス形状・エラー分類・レート制限ヘッダについて消費側の主張 | 顧客によって発見される静かな挙動変更 |

**文書化済み**: 大規模な依存障害の大半の背景にあるのは目新しい攻撃ではなく、誰も所有していなかった未保守のコンポーネントだ。実務で所有者台帳がスキャニングツールに勝つ理由がこれだ。スキャナは指摘を出し、所有者のいない指摘は1四半期でバックグラウンドノイズになる。

社内プラットフォームでも同じ論理が、より高い賭け金で適用される。こちらの依存先は他チームのコードだからだ。プラットフォームのコンポーネントには、日付付きの廃止ポリシー、アップグレードウィンドウ、可能なら移行を自動で行うツールが必要だ。消費者が移行する速さ以上で破壊的変更を出すプラットフォームチームは、プラットフォームを作ったのではなく自分の仕事を全消費チームへ同時に外注したことになる(移行戦略の章)。

## 購入したコンポーネントの失敗モード

| 失敗モード | 症状 | 修正 |
|---|---|---|
| 孤児化した重要依存 | 所有者なし、changelog未読、3サービスに存在 | 所有者台帳および既定ルール。無所有の依存は採用ではなく削除される |
| 静かな推移的導入 | テスト専用ツールがランタイムライブラリを本番イメージへ入れる | ビルドステージ分離。ソースツリーではなく出荷成果物をスキャンする |
| 出口なき抽象化税 | 1プロバイダを下手にモデル化する汎用インターフェース | 抽象化を消すか第2実装を足す。意図的に決める |
| 境界をまたぐリトライ増幅 | ベンダー劣化が自爆障害を起こす | リクエスト経路ごとに1つのリトライバジェット、呼び出し側が所有。負荷テストで検証 |
| ステータスページ楽観主義 | ベンダーは「劣化」と報告し、こちらは停止中 | 自社でベンダーテレメトリを保持し、自分のエラーバジェット消費でアラートする |
| 価格モデルの誤算 | リクエスト単価やエグレス課金がリトライとポーリングに比例して増える | 導入前に10倍でモデル化し、統合用のコストダッシュボードを追加 |
| データフローの漂移 | ベンダーSDKが誰もレビューしていない収集項目を増やす | エグレスは設計時に分類し、許可リストプロキシでCIの送信先を検査する |
| ビルド時の侵害 | 予期しないインストールスクリプト、未レビューなロックファイル変更 | 密閉ビルド、ハッシュ検証、そしてロックファイル差分をセキュリティ上のレビュー対象として扱う |

## 主要な要点

- 依存の決定はアーキテクチャの決定だ。失敗セマンティクス、アップグレード義務、データフロー、法的条件を同時にインポートする。プルリクエストに現れるのは最初の2つだけだ。
- マニフェストではなく解決済みグラフを数える。直接依存は選択、推移的依存は同じ爆発半径を持つ偶然だ。
- 能力を削除する統制は検知に勝る。許可リストプロキシ、ダイジェスト固定、ハッシュ検証、密閉ビルド、最小権限パイプラインは、どんなスキャナも確実には捕まえられない攻撃クラスを閉じる。
- 到達可能性の解析は払い戻せない脆弱性バックログを、誰かが終わらせられるパッチキューへ変える。重大度だけのトリアージはノイズと先延ばしの責任を生む。
- ロックインは5次元(データ形式、APIの形、運用、経済、スキル)にわたる出口コストで、その大半に対する正直な緩和策は抽象化ではなく書かれた出口ノートだ。
- 実際の世界第2実装か保護されたドメイン境界もないのに、プロバイダ非依存インターフェースを作ってはならない。さもなくば1社を下手にモデル化するための税を払い続ける。
- サードパーティは信頼できない依存だ。タイムアウト、バジェット付きの境界リトライ、ベンダー別バルクヘッド、冪等性キー、検証するWebフック、自社によるベンダーテレメトリが封じ込めの最小セット。
- ベンダーの可用性目標は自社の目標と合成しない。同期するサードパーティはSLOバジェットの行に置き、載らないならリクエスト経路から外す。
- 第2プロバイダへのフェイルオーバーは、ゲームデーで本番トラフィックを切り替えるまで未検証だ。不可能ならその事実と補償統制を記録する。
- アップグレードは所有者・レーン・EOLカレンダーを持つ常設プログラムだ。依存負債は他社のリリース周期という利率で複利化する。
